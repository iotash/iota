## 终端拥有屏幕

启动后第一帧进入 alt 屏（`ESC[?1049h`），退出时离开（`?1049l`）。之后所有字节都可以用绝对寻址：alt 屏没有历史、没有 reflow。inline 时代自研终端（X-54）的唯一理由——主屏上的绝对行号会在 resize 竞态中失效——在这里不存在，所以直接用 ratatui 自带的 `Terminal`（`Viewport::Fullscreen`）+ `CrosstermBackend`（`src/ui/runtime/screen.rs`）。backend 外面套一层 `Out`：尺寸取自最近一次 resize 事件，光标位置取自最近一次设置——**循环里零次光标查询**：启动、resize、退出都不发 DSR，对 DSR 不应答的终端也能运行。唯一的例外在循环之外：两个启动探测（OSC 11 查背景色，`osc.rs`；OSC 7501 查 herdr-core，`host/hc.rs`）各跟一个 `ESC[6n` 当读取终止符——在两者都不应答的终端上，第一个按键会被吞掉。

**布局**：自上而下 `[对话视口][帧]`。帧是 `FrameView` 的行（预览、分隔线、composer、状态行、补全列表、surface；`render/frame.rs` 沿用 inline 时代的帧，只加了补全列表的槽位、矮终端的让行 `shed` 和命中测试用的 `FrameMap`），固定在屏幕底部；视口占其余全部。对话从视口顶部开始、向下长（owner 2026-11-17，sel-top：所有聊天界面的模型），内容少时空行在它下面、帧的上面；只有比视口高时才跟随末尾，最新一行在视口最后一行，窗口随之滚动。新会话的 banner 和启动时 resume 回放的最后三轮从顶部开始；`/new` 和会话切换不清屏，分隔线接在已有对话之后。

**composer 和用户块**（owner 2026-11-16）：composer 没有提示符——输入的文字从第 0 列开始，续行也从第 0 列开始，真实光标（IME 锚点）就在文字所在的列，折行宽度是整个终端宽度（`input/composer.rs`）；上下两条分隔线已经把它和对话分开。提交后的用户块：每一行都以 `▌ ` 开头（折出来的行也是），文字对齐在第 2 列；用户块是**反显**，前面一条 bar（owner 2026-11-16 第四次——第三次的灰气泡撤回：反色那一对才让用户块和正文区分开）：每一行是**一个** `\x1b[7m` 反显 span，从第 0 列到行尾——背景是终端的前景色、文字是终端的背景色，没有一格露出终端背景（owner 2026-11-16 第五次：bar 那格在反显区外时，看起来像块缺了一角）。第 0 列是 bar，只有一格，**每一行都是 `▌`**（owner 2026-11-16 第六次：块的左边是一条从头到尾连续的柱），用户自己输入的块是中灰 245（`theme::USER_BAR`），带 tab 的块（宿主的消息）是青色 30（`theme::HOST_BAR`，#008787；owner 2026-11-18，见 block-hue 设计：色相说「另一个发送者」，深浅终端都可读，tab 的深色墨在上面仍是 AA 4.82:1），两者都写成**背景** `48;5;N`：反显会交换前景/背景，所以背景属性才是字形的颜色，而格子底下显示默认前景，正是块的颜色（写成前景 `38;5;245` 的话，反显后整格变灰、`▌` 变成终端背景色，又是一个缺口）；接着 `\x1b[49m` 恢复默认背景、反显保留——spans 解析器把 49 读作 `bg = None`，可以往返。第 1 列那个空格是块的第一格，文字从第 2 列开始，按显示宽度补空格到 width − 2，再一个 `RESET`，所以整块仍是满宽（`block.rs` `UserBlock { tab, text }`，`tab` 只有宿主自己的消息才有，见下）。反显与深浅主题无关，live 块和 resume 回放画出同样的行。`NO_COLOR` 下用户块不写任何转义：它的行是会话文本，退出时 `write_out` 原样写到主屏、不经过 spans 的颜色闸门，所以每行只剩 `▌ ` + 文字 + 补白，由 `▌` 这一列标出块；宿主的块和用户输入的块此时只差 tab 那一行（bar 字形只有一个）。状态行也从第 0 列开始——原来的两格缩进是为了对齐旧的 `❯ ` 提示符。`❯` 只剩 `/model` 组合框输入框自己的边（`surface/panels.rs`），与 composer 无关。

**宿主自己的消息**（owner 2026-11-17，X-107）：herdr-core（`hc`）把子代理的消息包成 `<hc from="…">…</hc>` 送进对话。这个元素**属于宿主，不属于文本**：宿主实现 `host::MessageEnvelope`，`Presenter::message_element` 给出第一个有这个能力的宿主的元素名——今天只有 `hc::HcHost` 认领 `hc`，herdr 多路复用器、cmux、普通终端都不认领任何名字，所以那里什么都不解析。提交路径在启动时问一次 presenter（`Transcript::set_claimed_element`，经 `Ui::user_block` 交给块），resume 回放和 `/session` 回放传给 `echo_rounds`；块只解析交给它的那个名字（`UserBlock::new(message, claimed)`）。消息去掉首尾空白后恰好是**一个这个名字的**元素时，用户块只显示内文，标签和属性画成块的第一行：一个 tab，`hc k:v k:v`，就是工具调用标签去掉方括号的那几段（同一个 `ToolLabel`、同一个 `… +N args` 尾巴），文字从第 2 列开始，和块的文字对齐；底色跟着 bar 走，是宿主块的青色 `48;5;30`，从第 0 列铺到文字后一格，没有 `▌`、没有边框。墨色是一种深色 `38;5;16`（名字粗体、键暗、值普通）：标签自己的青色在原来的灰上只有 1.7:1，深色墨在青色上是 4.82:1。别的名字、前后有文字、自闭合、未闭合、不匹配或内文不配平（`<hc><hc>x</hc>`），都照原样显示，没有 tab。提交路径看的是**完整文本**（`Transcript::user_input` 读 `Input::text`，粘贴全部展开）：`hc send` 是粘贴，超过 20 行的报告在有界的 `display` 里没有 `</hc>`，所以认领时块拿到完整文本，粘贴的界（20 行加 `… +N more lines`）只作用在内文上——标签头总在，live 和 resume 一致。tab 由标签自己截到行宽（值截成 `…`，还放不下就连这一对也丢，变成 `hc … +N args`，最后才截整段），画笔不再截。tab 这一行是块文本的一部分：选择、复制、搜索都读到 `  hc from:worker-2`（和 `▌ ` 一样），退出时也写到主屏。在 herdr-core 里，用户**自己**粘贴的 `<hc …>…</hc>` 也会被认领，显示成 tab 加内文，但模型收到的仍是完整原文（只改显示，不改 `Input::text`）。**为什么归宿主**：第一版是「任何一个 XML 元素都解析」，owner 否了——用户粘贴给模型的 XML 片段会被吃掉外层标签；归宿主之后，粘贴的片段（包括 herdr-core 之外的 `<hc>`）一个字节都不变。`NO_COLOR` 下 tab 是纯文本行 `  hc k:v`。live 块、resume 回放和退出时的写出都走 `UserBlock`。

**每帧路径**：一次循环迭代 = 布局 → `Buffer::diff` → 一次写。X-55 的规则不变，只是从 `InlineTerminal::commit` 移到了 backend 之下的 `SyncOut::commit`：一次写超过 `SYNC_MIN`（1024 B）就包成一个 DEC 2026 同步块，小的裸发。循环外的一次绘制（会话选择器）也是一次写。

**resize = 整屏重画**：SIGWINCH → 记下尺寸 → 安静 `RESIZE_QUIET`（50 ms，纯节流）后交给屏幕 → 下一帧 `autoresize` 清屏并重画每个格子。没有拖动协议、没有 band、没有少几列的帧。

**流式输出**：跟随尾部、几何不变、新增 `0 < n < 视口高` 行时，用一次 `DECSTBM 1;h` + `SU n` + `ESC[r` 滚动视口，只写新行（`Screen::scroll_region`；先把上一帧缓冲上移 n 行、在 backend 静音时用 `current_buffer_mut()` + `apply_buffer()` 交给 ratatui 当作"上一帧"）。M2（tmux 3.8，120×40）：打 11 个字符 11 B；`stream 100 20` 5 558 B（inline 8 982 B）；30 步拖动 21 032 B（每步整屏重画，按设计）。

## 对话缓冲（`screen/conversation.rs`）

- 缓冲存的是**块**（`ui::block::Block`，S7a，见下节"块模型"）：固定的行，或者带着源、按宽度布局的块。每块在某个宽度下的显示行在第一次被画到时算出，连同宽度一起缓存；只有可见行经过 `ansi_to_spans`。**不存 cell**。
- 上限 20 万**块**；超出丢最旧的，每块整个丢（一张表不会剩半张），并在顶部放一行 `earlier output trimmed — /export has the full text`。M1：10 万行 RSS +16.0 MB（S7b，三次跑 +16.00/+16.02/+16.01 MB；S2 时 +30.7 MB），一帧约 1 ms。一个 `Entry` 40 字节：放得下的行只存它的字符串和宽度，布局结果、续段标记和布局块的搜索文本在一个只有布局过才分配的 `Box` 里。
- 视图要么跟随尾部，要么锚在某一块（`Pos{row, line}`：块号、块内行）上；resize 后停在同一块（块内行夹到新高度）。上滚后新输出不拖动视图，视口最后一行显示 `↓ N new lines · Ctrl+End`。
- 提交的块原样入缓冲（不在提交时按 width−1 预折行）。帧里只有工具调用的预览（`render/region.rs`）；暂存窗口（尾部暂存行、残留、`rebalance`/`retrim`/`fit_width`、溢出分块）在 S7b 删除——它存在是因为插进 inline 历史的行收不回，而缓冲收得回。
- **M1 的量法**：每个场景在自己的进程里跑（`m1_alone` 用 `--exact` 重新执行测试二进制）。同一进程里的两个场景共用分配器，前一个释放的页后一个白拿，所以同一个场景单独跑 +16 MB、和邻居一起跑 +50 MB（S7a 评审实测）。现在一个数只有一个意思；`IOTA_MEASURE_M1=1 cargo test --release --lib m1_ -- --nocapture --test-threads=1`。布局块（9 万块，其中 3 万布局块，三次跑）：提交加首帧 +4.06/+4.08/+4.08 MB，结束时 +24.62/+24.80/+24.66 MB；resize 后第一次查询 487/486/481 ms（S7a 是 680 ms，尺子的快路径省下的）。

## 块模型（S7a，`ui/block.rs`）

宽度变化时，对话从**源**重新布局，不再把别的宽度的行盲折。owner 的原话："拖放窗口时，输出区域元素的重绘：启动的 banner、表格、列表的左部换行对齐缩进、代码块、引用块"。

- **三种块**。`Block::Row(String)`：一条逻辑行，原样提交——段落行、标题、通知、活动行、分隔空行。它不依赖宽度：比视口宽就由屏幕折行（`wrap_ansi`），不宽就整行显示，所以变宽时段落会重新展开。`Block::Laid(Arc<dyn Layout>)`：带着源，`Layout::lines(width)` 在画的宽度下布局。`Block::Live`（S7b）：一个还在写的布局块，带一个 `LiveId`，见下节"实时块"。
- **块的种类就是源的类型**（`Layout` 的实现），下游没有任何代码按种类分支，所以不另带标签：助手 markdown 的五种缓冲块是 `markdown::Fragment`（代码、表格、列表、引用、行间公式）；用户块（`block.rs` 的 `UserBlock`，live 块和回放共用）；banner（`repl/render/banner.rs` 的 `Banner`）；文件改动的 diff 列表（`repl/render/group.rs` 的 `DiffListing`）；结构化错误（`transcript.rs` 的 `ErrorRows`）。图片仍是行：半块像素画按提交时的宽度缩放，不重排。
- **提交接口**：`Ui::print(Vec<Block>)`（原 `print_lines(Vec<String>)`）。markdown 的 `Writer` 自己不再按宽度布局任何东西：缓冲块关闭时以 `Fragment` 交给 sink（`Sink::write_block`）；文本 sink 按自己的宽度渲染写出。生产环境里唯一的文本 sink 是引用块的子文档（`blocks/quote.rs` 的 `BufSink`），另外就是测试用的 `new_writer_to`。终端的 sink（`repl/render/uisink.rs`）和回放的 sink（`replay.rs`）保留源。
- **缓存与惰性**：缓冲在第一次需要某个宽度时调用 `Layout`，结果连同宽度缓存在块上；宽度一变，下一次画只重新布局它碰到的块（视口里的、滚动经过的），其余的等视图到达它们时再说。一次提交一大批块时（几万个），第一次画也只布局视口里那几块：`take_fresh` 从尾部数新行，数到视口高度就停。从来没被画到的块，由第一次需要它的搜索布局一次，之后就有了搜索文本。
- **搜索**：命中记为（块号, 块内第 k 次出现）。搜的文本与宽度无关：行块用它的原文（折行不会切断匹配）；布局块用它**第一次**布局时、在那个宽度下的纯文本行，以 `\n` 连起来，存下后不再变。所以 resize 既不重扫，也不为搜索布局任何块。跳转只布局落点那一块和它周围一屏，在新宽度下数出第 k 次出现在哪一行。搜索开着时 resize，视图会回到当前命中。代价有两个：布局块多存一份纯文本；表格在新宽度下如果把一个词折断，第 k 次出现可能数不到，这时跳到块的第一行。
- **上限按块计**，不按行或字节：一个块不论多高都算 1。评审 S2 之后，diff 只存预算内的行（`DiffRows`），剩下可能很高的块只有模型输出本身。评审实测：3 万个布局块全部缓存后 RSS +38 MB。不按源行数加权，是因为那需要每种 `Layout` 报告自己的大小，而 20 万块的上限在实际会话里远远够不到。

## 实时块（S7b，C10）

一个还在写的代码块、表格、列表、引用或行间公式，**在对话里逐行出现**，不再是帧里的一行计量（`rendering table… · 37 lines`）、关闭时才整块出现。

- **生产者**：`markdown::Writer` 每收一行，就把打开的块按当时的样子（一个 `Fragment`）交给会显示打开块的 sink（`Sink::shows_open_blocks` → `Sink::grow_block`），关闭时再交一次（`write_block`）。文本 sink（引用块的子文档、管道、回放）不显示打开的块，`Writer` 也就不为它做快照。代码逐行高亮（`highlight::LineHighlighter`，语法状态在行间延续），没有一行被高亮两次；关闭时的块和逐行长出来的块是同一个。
- **提交**：终端的 sink（`uisink.rs`）把它提交成 `Block::Live { id, layout, open }`，同一个块每次用同一个 id，关闭那次 `open: false`。第一次提交对 transcript 来说是内容：latch 里攒着的分隔空行先放出来，所以打开的块和关闭后的块间距一样（原来的 `flush_pending`/`preOpen` 删了）。之后的提交是替换，不是新内容：`ContentCommitter` 直接放行，不开新块、不放 latch。
- **缓冲（按 id 替换）**：`Conversation` 记着那个还开着的块（id 和块号）。同 id 再来就**原地替换**那一个 entry：它缓存的显示行、续段标记和搜索文本都丢掉，下次需要时从新源重算。锚点是（块号, 块内行），所以视图停在同一块上（块内行夹到新高度）。上限把它算作一块。最低的被替换块号报给搜索（`take_changed`），搜索从那里重扫。它在尾部长出的行算进 `take_fresh`，所以流式时仍是一次 `SU n`。
- **写出**：Ctrl+O 写到还开着的块之前为止，块关闭之后再写，整块只写一次，用那次写出时的宽度。退出时全部写出，包括还开着的块（不会再有内容了）。
- **宽度**：打开的块和别的布局块一样，在画的宽度下布局，所以流式中途 resize 会把已经到达的部分重新布局。
- **选择**：拖选时视图被按住（`hold`），块在指针下长也不移动；松开时复制当时的行。
- **代价**：打开的块每变一次，下一帧就整块重新布局一次，所以每帧的代价和块的大小成线性。S7b 评审单独计 `draw_frame`（release，高亮的 Rust 代码）：

  | 块的行数 | 2 000 | 4 000 | 10 000 | 20 000 |
  |---|---|---|---|---|
  | 每帧 | 6.2 ms | 10.3 ms | 26.4 ms | 50.3 ms |

  生产侧：feed 累计 2 000 行 0.93 s、20 000 行 12.6 s，略超线性，因为 `CodeBlock::fragment` 每来一行都复制一遍整段高亮文本；push 累计 20 000 行 1.8 s。一个 2 万行的块大约被限到 20 帧每秒。M1（`m1_a_growing_code_block`：2 000 行，每行一帧，含 feed、push 和画，三次跑）：全程 7.39/7.40/7.43 s；最后一行 6.05/6.04/6.11 ms；最慢的是第 0 行，42 ms（syntect 第一次加载语法）；RSS +27.3/+28.0/+27.5 MB。真实循环里一次迭代只画一帧，同一帧到的几行只付一次。原来每帧约 26 ms：尺子（`str_width`）对每行做 grapheme 切分，`ansi_width` 每行复制一份；现在可打印 ASCII 直接按长度量，不含转义的行不复制。
- **公式**：行间公式也逐行生长，但关闭前显示的是**线性源码**（半截的 LaTeX 排不成二维），收到结尾的 `$$` 才排成二维。代码围栏遇到一个没闭合的公式时，公式按当时的样子关闭（线性源码排版），代码在它下面另起一块；围栏关闭后的行就是普通文本——和纯文本渲染的结果一样（Go 会在代码之后续上公式，见 X-103）。
- **同一时刻至多一个打开的块**：`Conversation` 只记一个打开的块。现在每轮只有一个 markdown 生产者，所以成立；两个生产者交错的话，前一个的下一次 grow 会被追加成重复块。
- **`↓ N new lines` 数的是块**：往回滚的时候，尾部那个块原地长了 400 行，提示仍是 `1 new line`（S7a 起就按块数，S7b 让差距更明显）。留给 owner 决定（X-98/X-103）。
- **删掉的**：`markdown/preview.rs`（`PreviewHandle`）、`Sink::block_preview`、`UiStreamSink::block_preview`、`ui::sink::PreviewWriter`、`count_lines`、`PREVIEW_COUNTER_EVERY`，以及暂存窗口整套。

|---|---|
| banner | **重新布局**，不截断：同一份 facts，宽了卡片回来、窄了三行裸排、目录按新宽度从中间截。截断是不可逆的——窄过一次再拉宽，路径就永远是截过的；重新布局的代价是零（`Banner::lines` 本来就是宽度的纯函数） |

## 不归点：第一帧

全屏在**第一帧画出时**才进入 alt 屏（`Screen` 的 `Place::Main` → `Alt`）。在此之前终端上什么都不写，所以第一帧之前就结束的运行——`--help`、解析不了的配置、不存在的会话、`Tui::start` 之后第一帧之前的任何错误——都不会离开 shell 的屏幕，报错直接出现在 shell 里（L4 43）。没画过帧就退出时，缓冲里已有的行照常写进主屏，并且不会发出任何 alt 屏序列。会话选择器（`iota resume` 不带 id）也在全屏上运行；它的对话为空，离开时什么都不写，连分隔行也没有。

## 每一种退出方式

| 退出方式 | 终端 | 对话 |
|---|---|---|
| Ctrl+D、`/exit`、空闲时 Ctrl+C | 离开 alt 屏，关闭 raw/粘贴/焦点 | 写出（见下文） |
| SIGTERM 一次、SIGHUP（终端还在） | 同上，走正常收尾，退出码 130 | 写出 |
| 第二次 SIGTERM（收尾被卡住时，例如某个 MCP 服务器不肯退出） | `restore_terminal`：如果还在 alt 屏就离开，然后关闭 raw/粘贴，`exit(130)` | 如果 UI 已经关闭则已写出；否则**不写** |
| panic（release 是 `panic = "abort"`） | panic hook **先**调用 `restore_terminal`，再报告，所以报告出现在 shell 的屏幕上 | **不写**（缓冲在 UI 循环线程上，hook 拿不到） |
| UI 循环出错返回 | `TermGuard` 恢复终端 | 不写 |
| 终端挂断（pty 关闭、`tmux kill-server`） | 已经没有终端可以恢复；`HangupWatch` 让进程在 2 秒内退出（L4 29、42 B） | 无处可写 |
| Ctrl+Z 或 SIGTSTP，然后 `fg` | 先把终端交还（主屏、cooked、关闭粘贴和焦点），再 `SIGSTOP`；`fg` 之后重新接管，下一帧进入 alt 屏并**整屏重画**当时的尺寸（L4 44） | 不写；`fg` 后对话原样还在 |
| SIGKILL | **无解**：不运行任何代码，终端停在 alt 屏和 raw 模式。用 `reset`（或 `tput rmcup; stty sane`）恢复 | 屏幕上没有，但会话日志里有 |

凡是"不写"的情况，对话都不会丢：会话日志（`messages.jsonl`）每追加一批就同步一次，`iota resume` 会把整段对话载回缓冲，`/export` 能导出全文。

## 写出策略（Ctrl+O 与退出）

- **每行只写一次。** Ctrl+O 写出此前没写过的行，退出时写剩下的；第一段（第一次有行可写时）前面有一行 `┈┈┈┈ iota transcript ┈┈┈┈`。原生 scrollback 里对话正好一份、顺序正确，Cmd+F 和 tmux copy-mode 不会重复命中。计划 D2 原本建议每次全量重写并接受重复；没有采纳，因为重复本身没有好处。
- **宽度**：每一段按写出那一刻的终端宽度折行。之后的 resize 不会回头改已经写出的行，那些行归终端所有，由终端自己 reflow。退出时写的那段用退出时的宽度。
- **写出期间**：不画任何东西，新输出照样进缓冲；下一个键（不管是什么）回到全屏并整屏重画，这个键本身被吞掉。如果写出期间退出，就不再发第二次 `?1049l`。
- **与搜索叠加**：搜索中按 Ctrl+O，写出的是**原样的行**（不带高亮）；回来后搜索仍在原处。搜索中退出，同样写原样的行。
- **上限**：写出之前就被 20 万块上限裁掉的块，用"更早内容已裁剪"那一行代替。
- **挂起**（Ctrl+Z/SIGTSTP）不写出：`fg` 会把全屏原样带回来。

## 事件源（为什么用 `use-dev-tty`）

crossterm 0.29 默认的 unix 事件源（mio、边沿触发）有两处会让终端失控：
1. 同一次 poll 里 resize 和按键一起就绪时，它先返回 resize，丢掉 tty 的就绪状态。边沿触发的注册在**新**输入到来之前不会再报告，所以那个键要等到下一次按键才被读到（L4 42：40 轮里有 6–8 个键卡住；场景 39 的空闲 Ctrl+D 就是这样"丢"的）。
2. 读取循环只在 `WouldBlock` 或解析出事件时才退出。如果 tty 在 `HangupWatch` 判定"可读"之后才挂断，它会对着 EOF 一直空读，于是进程成了孤儿（PPID 1、`R` 状态、100% CPU）。L4 42 B 在旧事件源上 120 轮复现了 5 次，换成新事件源后 160 轮 0 次。

`use-dev-tty` 换成 crossterm 另一个电平触发、先读 tty 再读 SIGWINCH 管道的事件源，两处都消失了。它在零超时下什么都不读，所以 `HangupWatch` 等待之后，用 1 ms（`CROSSTERM_SLICE`）去问 crossterm。（S4 时 inline 也换了；S5 起只有一个世界。）

## 鼠标（S6，tui-plan D1/D3）

**默认开 capture，配置可关。** 终端不再滚动之后，滚轮是唯一自然的滚动手势（Claude Code 默认同样）。进入 alt 屏时请求 `?1000h`（按下/松开）、`?1002h`（按住时的移动，即拖动；不要 1003 的每次悬停）、`?1006h`（SGR 坐标，没有 223 列上限）；**每一条离开 alt 屏的路**——写出（Ctrl+O）、挂起、退出、`restore_terminal`（panic、第二次 SIGTERM）——都先关掉它，所以主屏上终端自己的选择永远可用。

| 位置 | 滚轮 | 左键 按下 / 拖动 / 松开 |
|---|---|---|
| 对话视口 | 一格 3 行；上滚暂停跟随，滚到底恢复跟随 | 选择：拖选、双击选词、三击选整行；松开复制 |
| 视口末行 `↓ … Ctrl+End`（已上滚时） | — | 回到尾部 |
| 搜索行 | — | 已应用的查询重新可编辑（保留查询） |
| surface | 移动列表（View：3 行） | 不在光标上的行：光标移过去；光标所在的行：**选中**（Enter 的路径；多选是 Space 的勾选）；tab 标签：切换；提示行：聚焦搜索框 |
| composer | 滚对话 | 光标放到指针下（宽字形的第二列算这个字形） |

**一次误点不会回答对话框**：surface 的一行要点两次（第一下移光标，第二下选中）——审批对话框里"Always allow"不该被一次手滑选中。

拖动按住在视口**顶行**或**末行及以下**（帧里）时，每 40 ms（`EDGE_STEP`）滚一步，指针不动也继续，所以一次选择能跨很多屏（opencode #61053 的反例）。只有拖动才滚：按下后指针还没动过（没来过 Drag 报告）就是点击，按住多久视口都不动，循环也不为它醒来；第一个 Drag 报告之后才按上述节奏滚，直到松开。顶行每步 1 行；视口下方按指针越过末行的距离加速，每步 1、3、5 … 行（帧的行数就是这个距离）。即便如此，**几百屏的大段复制请用 Ctrl+O 加终端自己的选择**：顶行方向最快每秒 25 行，500 屏要几分钟。时钟在循环的 poll deadline 里（W10 照旧有限）。

**松开丢了**（指针在窗口外松开、Cmd+Tab 切走）：任何按键、窗口失去焦点、resize 都结束拖动——按键丢掉选择，失焦和 resize 当作松开。否则边缘滚动会一直滚下去（S6 评审 SF1）。

**按下就固定视图**：在对话上按下开始选择时视图被"按住"（`Conversation::hold`）：跟随中的视图锚在当前顶行，新输出不移动指针下的文字；末行照旧报 `↓ N new lines`。松开时放开：仍显示最后一行就恢复跟随，否则停在原处。

**抖动不算拖动**：同一行上至少跨 2 列（或换了行）才算选择；1002 下点击时抖一格只是点击，不会覆盖系统剪贴板。

## 应用内选择（`render/selection.rs`）

- **点是缓冲里的格，不是屏幕的格**：(行号, 折行内第几行, 显示列)。块号按提交编号，所以 20 万块上限丢旧块不移动它；新输出到来时选择留在原文上。resize 换了折行，选择清掉。
- **画**：只改屏幕 cell 的 `REVERSED`，行本身不动——**写出（Ctrl+O、退出）永远不带选择的样式**（`screen::tests::the_selection_is_drawn_reversed_and_never_written_out`）。
- **复制的内容**：屏幕上看得见的纯文本——SGR 和 OSC 8 超链接都去掉（链接只复制它的文字，搜索也不会命中看不见的 URL）；一个布局出零行的块占一行空行（块的行数只有 `Entry::lines` 一个来源，视口、命中和三击都按它算）；**屏幕**把一行折成的几段拼回成那一行（缓冲按 `Block::display` 标出哪些显示行是续段）；其余的行，包括块与块之间、布局块自己的行（表格的、代码块的），之间都是 `\n`；行尾空白去掉。三击选指针下那一行连同它的续段，不是整块（S7a 评审 B1）。双击的"词"＝字母数字加路径/URL/标识符的标点 `_-./~+:@\`，句末的 `.` `,` `:` 不算。
- **按键清掉选择**（也结束一次没收到松开的拖动）；单击（不拖，或只抖一格）什么也不选、不复制。
- **复制路径**（`runtime/clipboard.rs`；X-109，owner 2026-11-19，推翻 11-16 的"只走一条"与"状态行不提路径"）：
  - **不在 tmux 里（GNU screen 里也一样）：本机工具和 OSC 52 同时走**，SSH 与否都一样。本机工具（`pbcopy`；`wl-copy`/`xclip`/`xsel`；`clip`）写的是 iota **所在机器**的剪贴板；OSC 52 让**用户面前的终端**写它自己的。用户在看哪台机器，环境变量判断不了：herdr-core（`hc`）从另一台机器 attach 的终端里没有任何 `SSH_*`、没有 `$TMUX`，`TERM_PROGRAM` 还是对端的 `ghostty`——只挑一条时 iota 跑了 `pbcopy`，文字进了远端 iMac 的剪贴板，owner 在笔记本上什么也粘不出（诊断：`copy-why.md`）。两条都发：真在本机时同一段文字写两次，无害；终端不认 OSC 52 时序列被丢弃，无害；代价一是 SSH 到一台有 `pbcopy`/`xclip` 的远端时，远端的剪贴板也被写（以前不会）；代价二是本机 iTerm2 用户以前从不收到 iota 的 OSC 52，现在首次复制可能弹出许可（iTerm2 默认关闭剪贴板访问）。**不做**"`127.0.0.1` 算本机"之类的启发式：那台机器上的回环地址恰好是 Surge 的中转，人在别处。
  - **在 tmux 里（`$TMUX`）照旧**：写 `tmux load-buffer -w -`（`-w` 让 tmux 按 `set-clipboard` 再交给外层终端），不在 SSH 下时再加本机工具；OSC 52 只在这些全部失败时才发（tmux 本来就会把它转出去，不该写两次）。
  - **在 GNU screen 里（`$STY`，`$TMUX` 未设时才看）与外面相同**：`[Local, Osc52]`，SSH 与否都一样，只是序列按 76 字节切块、每块包成 DCS 串 `ESC P … ESC \`（`screen_dcs`，hterm 的 `osc52.sh`、vim-oscyank 的做法）。screen 把 DCS 串的内容原样交给外层终端；裸的 OSC 52 则短的被吞掉，长的大半被当成文字打在屏幕上（4.00.03 实测：3000 字节的序列有 1790 个字符落在屏上），而 iota 按差异重画，不会擦掉它们。4.00.03 实测（copy-a12）：拖选 4290 个字符（序列 5728 字节），外层终端收到完整的一条 OSC 52，解码与 `pbcopy` 收到的相同，屏上 0 个乱码字符。
  - 每个外部程序是自己的子进程，stdin 由各自的线程写入，卡住的既不拖住循环也不拖住别的程序（`pbcopy` 卡住，`tmux load-buffer` 照跑）；循环轮询各自的退出。超过 `COPY_DEADLINE`（2 秒）还没退出的被 kill 并按失败结算（`Pending` 的 `Drop` 负责 kill 并回收：到期结算、2 秒内再复制一次替换掉它、退出时还挂着，都不留子进程），已成功的照算——`pbcopy` 卡住、tmux 成功得 `(tmux)`；一个都没成功时 tmux 外状态行写 `(OSC 52)`，tmux 里走 OSC 52 兜底；OSC 52 序列在复制开始时就和那一帧一起写出，不等工具。**至少一条路走通就算复制成功**：工具成功，或序列写出了（OSC 52 报不回结果）；工具失败不影响 OSC 52。
  - OSC 52 序列有上限 `OSC52_MAX`（100 000 字节，约 73 KB 文本；hterm、tmux 也在这个量级截断）：超过就不发，但本机工具照样能接——那时状态行明说终端没收到：`copied N characters (pbcopy; too large for OSC 52)`（只在 tmux 外，那里序列本该同发）；没有工具接住才是 `not copied: N characters is too large — use Ctrl+O`。
- **提示**：复制后状态行 4 秒内显示 `copied N characters (pbcopy + OSC 52) · Shift+drag selects in the terminal`，括号里是**实际走通的路**：成功的程序按文件名（`pbcopy`、`xclip`、`tmux` …），再加写出了的 `OSC 52`——两条都走 `(pbcopy + OSC 52)`，只有一条 `(OSC 52)` 或 `(pbcopy)`，tmux 里 `(pbcopy + tmux)`。**为什么要说**：11-16 的决定认为"`OSC 52` 对用户没有意义"，但"进了另一台机器的剪贴板"和"真的复制了"说成同一句，用户和排查的人都分不出来——这次排查绕了两轮正因为此。iTerm2（`TERM_PROGRAM=iTerm.app` 或 `LC_TERMINAL=iTerm2`）显示 `Option`。一句话，不是段落（`vt100_tests::the_copy_status_names_the_ways`）。

## 关闭开关（`mouse: false`）

`~/.iota.yaml`（或项目的 `.iota.yaml`）顶层 `mouse: false`。之前没有任何 UI 设置项，这是最小的那一个：顶层标量，和 `write_roots` 并列，YAML 1.1 布尔，栈里最后一个写它的文件说了算。关了之后**一个鼠标序列都不写**（不请求也不"关闭"），终端自己的选择照旧，跨屏选择先 Ctrl+O 写出。**滚轮归终端，但终端拿它做什么不由 iota 决定**：tmux 3.8 在 alt 屏里什么也不做（L4 47 断言了：不进 copy mode、不变成 ↑↓）；不少终端默认在 alt 屏里把滚轮变成 ↑/↓——iTerm2 的 "scroll wheel sends arrow keys in alternate screen mode"、Terminal.app、WezTerm 的 alternate scroll——而 ↑/↓ 在空 composer 上会翻输入历史（X-89），这正是 X-102 不用 1007 的理由。这些终端里 `mouse: false` 的滚轮会翻历史而不是滚对话；**没验证**（这里没有图形终端），列在 TUI-VERIFY §4c.7。键盘滚动不受影响。会话选择器（`iota resume`）同样遵守。

## surface 占视口（C13）

S5 时 surface 挤在帧行里：帧变高会把对话推走，所以 View 限 `min(lines,15)`、picker 预览限 `[4, h−12]`。现在 surface 画在视口的位置上：`Model::frame_view` 先量出帧自己的行（调用预览、间隔、队列、两条分隔线、composer），剩下的行是 surface 的 room（`SurfaceState::set_room`，连同屏高），视口让出 surface 实际用到的行；关掉 surface，视口拿回来，对话停在原处（跟随时仍是尾部，锚定时仍是那一行）。面板的行数受**交互区上限**约束（`crate::ui::interaction_rows`，和补全列表同一条规则）：**一个交互区永远不超过半屏、也不超过 15 行**（`INTERACTION_MAX_ROWS = 15`），即 `min(room, min(15, 屏高/2))`，且上限不低于 `SURFACE_MIN_ROWS`——50 行的屏 15、40 行 15、24 行 12、12 行 6（12 行时帧只给 `/file` 的列表留 5 行，room 更小，取 room）。多出来的内容在面板里滚动，对话保留其余的行（owner 2026-11-16：`/file` 的目录浏览器占了整个屏幕）。窗口跟着光标：100 个条目、12 行的列表，`↓` 走到第 13 项时窗口下移一行，`→`/`←`（PgDn/PgUp、Ctrl+F/B）翻一页，`g`/`G` 到首尾，提示行末尾是滚动百分比，最后一项总能到达。显式 `height` 保持原义，只以 room 为上限（可以超过交互区上限）；picker 预览没有显式 `height` 时同样不超过上限（`min(14, 上限)`），再夹在 `[min(4, room), room]`。面板的 room 是 `Option<Room>`（空闲行数 + 上限）：只有没被循环布局过的 surface（单测里的）是 `None`，这时取 15。**room 至少是 `SURFACE_MIN_ROWS`（5 行）**：帧自己的行就把屏幕占满时（8–9 行的窗格里写满 5 行草稿、再有队列或预览），帧比屏幕高，这时屏幕保留帧的**底部**——surface 和它的提示行——让上面的预览和 composer 让出行（surface 开着时 composer 本来就不接键）；点击按被截掉的行数换算（`FrameMap::cut`）。否则审批框会整个落在屏幕外，Enter 回答的是看不见的选项（S6 评审 SF2）。surface 仍在 composer 下面：一个审批对话框要回答的那次工具调用就在它上方的视口里，盖住它反而看不见。

## 补全列表（`input/suggest.rs`）

inline 时候选项只能挤在 composer 块里的一行（宽度窗口 + `+N`），选中项的说明借状态行显示。现在屏幕是自己的，候选变成 fzf / Claude Code 那样的单选列表，在 **composer 上方**（中间空一行，见下）：列表向上长，composer、下分隔线和状态行都不动（owner 2026-11-16；之前它挂在下分隔线和状态行之间，向下长，输入时 composer 跟着跳）。
- **浮层**（owner 2026-11-17，sel-float）：列表的区域**画在对话上面**，不再从对话那里拿行。对话保留没有列表时的矩形（布局、跟随、滚动都按它算），帧画在这个矩形的最后几行之上（`FrameView::float`，`Screen::paint`），所以打开、收窄、关闭列表都不移动对话的任何一行；被盖住的行只是看不见——PgUp/PgDn 按可见行的一半翻页（不按矩形，否则会跳过从未显示的行）；它们没有 mark（选择和鼠标碰不到），`↓ N new lines` 和搜索行在**最后一个可见行**，流式滚动（`DECSTBM`）只滚可见行。对话从顶部开始（见“布局”），所以放得进可见行的对话一行都不会被盖；对话在列表打开时长过可见行，新行接在下面、落进区域底下（上面的行不动），长过矩形后才按矩形跟随末尾——和没有列表时一样。
- **区域就是列表**（owner 2026-11-17，sel-top）：区域高度是列表的行数加列表下那一行空行（见下条），顶边和列表之间不留空行。匹配收窄时列表变短，顶边跟着往下走，让出来的行露出对话原来的样子（对话从不移动，所以露出的就是它本来的行）；变多时顶边往上走。区域内自上而下：上分隔线（原来在列表和 composer 之间，现在是区域的顶边——“列表从这里开始”）、列表、一行空行、composer、下分隔线、状态行。
- **列表和 composer 之间空一行**（owner 2026-11-17，list-gap）：列表最后一行直接压在 composer 第一行上时两块读成一块，所以中间留**一行空行**（`frame::LIST_GAP`）。它是帧的行，不是列表的行：不铺底色，不在列表的点击范围里，点上去和点间隔行一样什么都不做；它和列表一起浮在对话上（`FrameView::float` = 列表行数 + 1），所以对话照样不动，只是可见行少一行。只在列表打开时有，关掉列表帧和以前一模一样。不用更淡的分隔线：第二条线会把 composer 框起来，而且 `NO_COLOR` 下它和上分隔线一模一样。不加底色和边框：顶边就是那条 faint 分隔线，`NO_COLOR` 下照样在。状态行始终是状态行。它不是 `tabbed-select.md` 的那个 surface：不接管按键，只在行是斜杠命令时出现，surface 打开时或搜索（`Ctrl+R`）进行时不画——搜索把命中放在矩形的半高处，区域会把它盖住；浏览命中时，除视图键外的键（字符、`↑`/`↓`、`Tab`）先结束搜索，所以它们碰到的列表一定在屏幕上。

- **每项的布局：两列**（owner 2026-11-16）。第一列是标记和标签：标记在第 0 列，和 composer 的第 0 列对齐，标签从第 2 列开始（高亮项是所有列表共用的「当前行」，X-106：青色 `▸`，该项的每一行——说明和续行也算——整行铺底色到右边缘；否则 `  label`；标签一律粗体、默认前景色，沿用旧规则，不重复已输入的 `/`）。标签列宽是**全部匹配项**（不只是窗口里看得见的）中最长标签的宽度，所以滚动时列不跳；上限 `LABEL_CAP = 30`（命令名和技能名都短），超出的标签用 `…` 截断。第二列是说明，暗色（次要文本），从标签列后空两列（`GAP = 2`）开始，第一行和标签同一行；按词折行，宽度 `min(剩余宽度, 72)`，**最多两行**，第二行同样从第二列开始（不会跑到标签下面），多出的在末尾用 `…` 截断。没有说明的项只有一行，标签列照样对齐。**72** 是终端散文的经典行宽（commit 正文、man page）：160、200 列的终端上说明仍是一小块，不会拉成一整行。
- **两列靠字重区分，颜色只是加强**（owner 2026-11-16）：每一行的标签都是粗体，说明都是暗色；高亮不给标签换色，只加青色 `▸` 和整行底色（`theme::row_bg`）。粗体和暗色是属性，`NO_COLOR` 下颜色和底色被丢掉而它们保留，所以关掉颜色两列仍分得开，高亮项仍有 `▸`。`BOLD` 和 `FAINT` 一样住在 `ui/render/theme.rs`。
- **键**：`↓`/`↑` 按**项**移动高亮（不是按行），循环；从无高亮开始 `↓` 到第一项、`↑` 到最后一项。每一步像 `Tab` 一样把该项的值写进 composer，所以 `Enter` 提交的就是高亮项；`Esc` 把行恢复成输入时的样子、去掉高亮，第二个 `Esc` 才到 turn 的 scope。`Tab` 不变。行不是斜杠命令时 `↑`/`↓` 仍是历史和队列。过滤规则（整行前缀、`/skills ` 之后才出现技能行）不变；技能行显示的是技能自己的说明。
- **窗口**按整项滚动：记住上一帧的首项（`Composer::suggestion_top`），只移动到让高亮项的**所有行**都在窗口里为止；下面空出来时往回补上面的项。
- **空间**：`Model::frame_view` 先量出没有列表的帧有几行，再减去空行，剩下的是列表的（和 surface 的 room 同一个算法；空行从屏幕里出，不从列表的上限里出），画在对话上面（不从对话拿行，也不从 composer 拿），并且和 surface 一样不超过**交互区上限**（`interaction_rows`：半屏、至多 15 行）——40 行的终端上 200 个匹配也只占 15 行，窗口跟着高亮，`↑`/`↓` 走到窗口外的项；空间不够一项时只画高亮项（无高亮时是第一项），不会消失。屏幕矮到连高亮项都放不下时（没有 surface），按优先级让行，从“永不截”到“最先截”：composer 永不截；高亮项（无高亮时是第一项）尽量完整，否则至少留它的标签行；状态行在高亮项丢一行之前让出；其他项更早让出（窗口缩到只剩高亮项）；对话最先。分隔线是装饰，可以丢。实际让行顺序：区域上方的行（间隔行、调用预览、队列，由 `FrameMap::cut_for` 从顶上截掉）→ 列表下的空行 → 下分隔线 → 上分隔线 → 状态行（`frame::SHED_ORDER`，`FrameInput::shed`）→ 高亮项的描述行（从下往上）。以 `investigate`（两行）为例：80×7 只少了间隔行；80×6 再丢空行；80×5 再丢下分隔线；80×4 是高亮项两行、composer、状态行；80×3 状态行也让出；80×2 只剩标签行和 composer。窗口外还有项时**不画** `… +N` 之类的标记（owner 2026-11-16：多占两行，Claude Code 和 Codex 也没有）。
- **鼠标**：点在一项的任意一行（标签行或说明的第二行）上都高亮那一项；`FrameMap` 记列表的首行和行数，`Model::list_items` 记每行属于哪一项。

## 明暗色调：运行中再问一次（X-108，owner 2026-11-18）

色调（`dark`）只是一个布尔值：列表当前行的底色（`theme::row_bg`，237 / 253）、面板输入框的底色（`theme::input_bg`，236 / 254）、代码主题和 diff 底色都按它取固定的 256 色。启动时问一次终端的背景色（OSC 11，`osc::detect_background`，在 loop 接管输入之前做一次往返）。系统在运行中切换明暗——日落时自动切，或者手动切——之后，iota 自己再问，**不需要重启，也没有手动开关**（没有 `/theme`，没有配置项）。

- **什么时候问**：只在两个时刻。① 窗口重新获得焦点（`FocusGained`），这一轮就问——loop 只写不读，用户正在打字也不受影响；② 两轮之间，`run.rs` 先问宿主（cmux 知道自己的背景），宿主不知道就走 `Ui::requery_background`，答案喂给原有的三个 setter（REPL 的标志、transcript 的 diff 底色、帧），所以 REPL 这边的副本和帧一起动。空闲时不轮询。
- **怎么问——loop 只写不读**：`osc::round_trip` 自己读 tty，只在 loop 启动前安全；放进 loop 里，回复到达之前敲下的键会被它读走，而 crossterm 没有办法把字节塞回去。所以 `runtime/requery.rs` 只把 `ESC ] 11 ; ? ST` 写进这一轮的 batch，然后回去读事件。crossterm 0.29 没有 OSC 回复这种事件，它把 `ESC ] 1 1 ; rgb:… BEL` 解析成一串按键：`Alt+]`、每个字节一个字符键、`Ctrl+G`（ST 结尾则是 `Alt+\`）。问题在途时，`ReplyMatcher` 从 `Alt+]` 起**吞掉**每个可能属于回复的键，遇到不可能属于的键就结束这一串并放行它；其余事件按原顺序照常处理——不扣留、不交还、没有定时器。**回复窗口里敲的键就是排在回复前面的普通事件：除了 crossterm 没有第二个读者去读它。** 代价：问题在途时手敲的 `Alt+]`（没有绑定任何功能）连同紧跟其后、可能属于回复的键会被丢掉，而不是延迟。有一个残余风险，接受而不消除：如果回复的第一个字节 `ESC` 恰好是一次读的最后一个字节（终端分两次写，或者传输层正好在那里切开），crossterm 会先送出一个单独的 `Esc` 键。matcher 从不吞单独的 `Esc`（它要取消 turn），所以这个 `Esc` 会生效——取消最内层的东西，包括正在流式输出的 turn——回复剩下的 `]11;rgb:…` 会被打进 composer。终端的回复是一次写出的，crossterm 一次读 1024 字节，所以这需要恰好切在第一个字节之后；tmux 里没有见到过。
- **不回答的终端只问一次**：100 ms 内没有回复就是 miss，本次会话不再问（`requery_background` 立刻回答 `None`）。matcher 的待命期是一个时刻——发出时间 + 100 ms + 1 s（`MISS_GRACE`）——在 `feed` 里比较，不需要定时器：这之前迟到的回复仍然被吞掉并忽略，之后不再匹配任何东西，晚于它才到的回复会被当成输入。
- **宿主知道背景时不问终端**：cmux 这类宿主自己回答背景色，`run.rs` 在第一轮之前告诉 loop 一次（`Presenter::knows_background` → `Ui::background_from_host`），焦点检查和两轮之间的询问都不再问终端，两个来源不会把帧的色调来回翻。
- **代价**：两轮之间的询问让每一轮开始前多一次终端往返——回答的终端上是几毫秒，不回答的终端上是一次 100 ms（miss 之后不再问）。
- **翻转就是普通的一帧**：`self.dark` 改掉、标脏，下一帧按新色调取色；不清屏，不 `force_clear`。已经提交的块保留渲染时的色调，**历史不重染**。
- **已知的限制**：不回答 OSC 11 的终端（Linux console、PuTTY、mosh、GNU screen）和 Windows（iota 在那里什么都不问）保持启动时的色调；延迟超过 100 ms 的链路按 miss 处理；herdr 0.9.5 里 pane 的回答在翻转后可能是旧值（herdr#4183，已在其 master 修复），那时问了也不变；窗口一直聚焦又没有新一轮时，切换要等到下一轮或下一次聚焦才被看到。
- **为什么不用 mode 2031**（终端主动通知，`CSI ? 997 ; Ps n`）：crossterm 0.29 的解析器永远不会结束这个序列，之后的按键全部卡在它的缓冲里。等解析器修好再订阅。
- 启动时的那次往返也改了：`osc::exchange` 带着同一个 100 ms 期限等描述符，不再把读交给一个脱离的线程——以前终端不回答时那个线程会一直挂在 tty 上，吃掉用户敲的第一个键。等待用的是 `select(2)`，**不是 `poll(2)`**：macOS 的 `poll` 不支持设备，对 `/dev/tty` 立即返回 `POLLNVAL`，用它写的等待等于没有期限，读会一直阻塞到用户按键并把那个键吃掉（评审时在本机复现）。这条路径由一个真实 `/dev/tty` 的测试钉住：测试二进制在 `script(1)` 下再跑一次，pty 什么都不回，往返必须在约 100 ms 后以超时返回。等待被信号打断（启动时调整窗口大小就是一次 SIGWINCH）不算超时，`exchange` 用剩下的时间接着等。`HangupWatch` 用的是同一个等待（`runtime/tty.rs`）：以前它对 `/dev/tty` 调 `poll`，并把 `POLLNVAL` 当成挂断，所以在 macOS 上 stdin 不是终端时，循环一启动就以 BrokenPipe 退出。现在它用 `select` 等待，只有"可读但队列里 0 字节"（`FIONREAD`；Linux 上挂断的终端对它回 `EIO`）才算挂断，同样由 `script(1)` 下的真实 `/dev/tty` 测试钉住。

## C11 从这里继承什么

- **C11（折叠块展开/收起）**若做，点击已经有路由（`input/mouse.rs` 的 `Target`）：视口里的一下按下目前是选择的起点，展开需要一个区分（例如点在折叠摘要行上）。展开/收起就是换掉一个块的源：S7b 的按 id 原地替换（`Block::Live`）已经是这条路。
