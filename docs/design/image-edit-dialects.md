# Image edit dialects across providers: how common is OpenAI's `/images/edits`?

Status: **Research memo, no code** · 2026-11-05 · `edit-survey` on `85a9ab2` (v0.7.7) · vendor reference pages read 2026-11-05 (cited per row) · live probes 2026-11-05 with the four keys in `~/.iota.yml` (§6)

The owner rejected a Venice-native edit mode inside `type: images` (Venice's `/image/edit` is another path, another body, a raw-file response). Question: among third-party image providers, how common is an OpenAI-compatible `POST /images/edits`, versus a vendor-native edit API — and does that bear the stance out?

**Short answer.** It does. Of the fourteen third parties asked about, **one** reuses the `/images/edits` path (xAI, with its own JSON body), **two** offer OpenAI's multipart form on that path and only narrowly (DeepInfra; Novita for a single model), **three** edit through a generations endpoint plus an image field (OpenRouter, Together, SiliconFlow — three spellings of the field), **five** are vendor-native (Venice, Replicate, fal, Stability, Google), **three** have no edit at all (Fireworks deprecated 2026-06-10, Nebius, Hyperbolic decommissioned). The compatibility layers that call themselves OpenAI-compatible stop at `images/generations` — Venice (swagger has no `images/edits`), Google, Alibaba (in writing: "`/images/edits`, multipart, `mask` not yet supported"). `/v1/images/edits` is otherwise a *gateway* path: Azure, LiteLLM, vLLM-Omni. The only edit dialect with more than one implementer is the one `type: images` already speaks. Every other dialect is one vendor wide, so "one provider type per wire dialect" means one type per vendor, each at the `imagen` type's cost (§4).

## 2. The count, and the dominant shape

Fourteen third parties asked about: OpenAI's `/images/edits` with OpenAI's body **2** (DeepInfra, Novita — one model), the path with a foreign JSON body **1** (xAI), generations + image field **3** (OpenRouter, Together, SiliconFlow), native **5** (Venice, Replicate, fal, Stability, Google), none **3** (Fireworks, Nebius, Hyperbolic). The eleven extras change nothing: Azure is first-party, LiteLLM/vLLM-Omni/Azure-AI-FLUX are gateways, Alibaba compat and Volcengine join the generations+image family (five members, **five spellings**: `input_references[{type,image_url:{url}}]`, `image_url`, `image`\|`input_image`, `image` string-or-array, `reference_images[]`), the rest are native.

The dominant *wire* shape is: the vendor's own path, a JSON body, the reference image as a **URL-or-data-URI string** (fal, Replicate, Together, SiliconFlow, Volcengine, Alibaba, BFL, DeepInfra native, Venice-JSON: nine), a wrapped object only at OpenAI-JSON `{image_url}`, xAI `{url}`, OpenRouter `{type, image_url:{url}}` — three wrappers, three spellings; multipart files at OpenAI, Azure, DeepInfra-edits, Stability, Ideogram, Recraft. Responses: OpenAI's `data[]` envelope at eleven (with `mime_type`, `media_type`, `type`, `image_id`, `is_image_safe` grafted on), a vendor envelope (`images[]`, prediction, `output.choices`, `result.sample`, `inlineData`, `predictions[]`) at ten, **raw bytes at two** (Venice, Stability; HF's task spec). Nine have an asynchronous path (Replicate, BFL, Novita, Alibaba i2i, Stability relight, fal queue, Ideogram, Runware, xAI `deferred`). Moderation has no majority spelling: `moderation low|auto` (OpenAI; Venice compat), `safe_mode` bool (Venice native), `safety_tolerance` as int 0–6, int 0–7 and string `"1"`–`"6"` (Replicate, BFL, fal — the same FLUX knob, three types), `disable_safety_checker`, `enable_nsfw_detection`, `safetySettings[]`, and **none at all** at eight (xAI, OpenRouter, Volcengine, Recraft, Stability, Ideogram, DeepInfra, Azure edits), which instead flag the output (`finish_reason`, `is_image_safe`, `has_nsfw_concepts[]`, `nsfw_content_detected[]`, `x-venice-is-blurred`). Size likewise: `size WxH` (OpenAI, Azure, DeepInfra, Alibaba, Volcengine, SiliconFlow), `aspect_ratio` (Replicate, fal, BFL-Kontext; with a resolution tier at xAI, Venice, OpenRouter, Google), `width`/`height` ints (Together, Nebius, Runware, Novita, BFL FLUX.2), nothing on edits (Stability, Ideogram, Recraft).

## 3. What an abstraction would actually unify

The *semantic* request is identical everywhere — model, prompt, 1..n reference images, optional mask, count, a size-or-aspect wish, a moderation level → 1..n pictures as bytes — and iota already owns it: `ImagesEditRequest` (`src/llm/images.rs`) plus the response reader that lands every form as bytes + mime (`src/provider/images.rs`, X-86). Nothing above that layer would change for any vendor in the table.

What does not unify is the wire, on four independent axes: **path** (one per vendor), **image encoding** (multipart part / base64 string / data-URI string / https-only string / `{url}` / `{image_url}` / `{type, image_url:{url}}` / `inlineData` / `bytesBase64Encoded`), **response envelope** (`data[]` / `images[]` / prediction / `output.choices` / raw bytes + headers / poll-then-fetch), and the two **vocabularies** (size: three spellings; moderation: six spellings or none). LiteLLM is the existence proof: its `/v1/images/edits` is fifteen hand-written translator directories, not a parameterisation. A "generic edit abstraction" in iota would therefore be either the semantic layer it already has, or a translator per dialect — which is what a provider type *is*.

## 4. Recommendation

**`type: images` is enough for the dialect it names, and the dialect is complete.** OpenAI multipart covers OpenAI, Azure, the gateways (LiteLLM, vLLM-Omni, Azure AI FLUX), DeepInfra's edits and Novita's Ming; the xAI JSON form covers xAI. That is the whole population of `/images/edits` endpoints found. No third vendor speaks either form, so there is no row waiting to be added to this type.

**The rejection of a Venice-native mode is right, for a reason stronger than taste.** Venice's `/image/edit` differs on all four axes at once (own path; base64-or-URL string body with `additionalProperties:false`; raw bytes with the verdict in headers; `safe_mode` + `aspect_ratio`/`resolution` instead of `moderation` + `size`), and its edit models are `type: inpaint` in `/models` (28 live, §6), which the `images` listing's `?type=image` never returns. A flag on `images` would put a third wire dialect behind one type name, chosen by config rather than by what the endpoint speaks; `json_edits` is already a two-dialect flag and must not become a registry. Venice also relays the very models `images` already reaches at their origin (`gpt-image-2-5-*-edit`, `grok-imagine-image-2-0-edit`), so the only thing a Venice type adds is Venice's own catalogue (`qwen-*-edit`, `flux-*-edit`, `seedream-*-edit`, …) under Venice billing.

**One provider type per wire dialect is the honest model**, and since every non-OpenAI edit dialect is one vendor wide, that means one type per vendor — exactly how `imagen` (Google `:predict`) already sits beside `images`. A Venice type would cost about what `imagen` costs: ~300 lines of provider (`imagen.rs` is 293) — a JSON builder reusing `image_util`, a raw-bytes reader with the two headers, an `inpaint` listing row under the model-listing rule (all four conditions, or none), `safe_mode` behind the Moderation switch and `aspect_ratio`+`resolution` behind the Image tab's size options — plus ~400 lines of tests (`tests/provider/imagen.rs` is 388), the type enum, `tuning::apply` warnings, `meta.json` replay, the mock in `src/testing/provider.rs`, a tmux scenario and DIVERGENCES rows: the nineteen touchpoint files `grep -rlE 'ProviderKind::Images|json_edits' src tests` names today.

**When it earns its place:** all three, not one — (a) a user wants a model only Venice serves for editing; (b) the surface has stopped moving (`inpaint` on `/image/generate` was disabled 2025-05-19, `modelId` → `model` deprecated, `/image/multi-edit` now beside it; a type pins a wire, and this one has moved every year); (c) no cheaper route exists. If a second edit type is ever built, Venice is not the cheapest candidate: OpenRouter's `/images` + `input_references` keeps OpenAI's `data[]` envelope, needs no raw-bytes reader, and is already the `output_modalities` listing row — but it is one vendor wide too, and today nobody has asked.

## 5. What not to do

- No `edit_dialect:` / `native_edit:` key on `type: images`, and no "try `/images/edits`, on 404 fall back to `/image/edit`" — a path probe needs a vendor identity, the case the listing rule already refuses.
- No config-described wire (path, field name, envelope, header names in YAML): that is LiteLLM's translator table handed to the user, with iota's tests covering none of it.
- Don't read "OpenAI-compatible" on a vendor page as covering edits. Venice, Google and Alibaba all say it and all stop at generations; only a dated probe or the vendor's swagger settles it.
- Don't route edits through chat completions: OpenRouter's chat image route is no longer on its image page; Google's `generateContent` is the `google` dialect, not an `images` variant.
- Don't send `moderation` on the multipart edit form (still absent from the schema, X-88 stands). But see §6: OpenAI's JSON edit form is the one place `moderation` reaches an edit, and iota's `json_edits` is xAI's JSON, not OpenAI's.
- Don't probe xAI's `/images/edits` with a body that has a prompt and no image: it is answered as a plain generation and billed (§6).

Calibration: `/images/edit` (singular) answers 404 at OpenAI, Venice, OpenRouter and 405 at xAI.

- **X-88 has drifted.** OpenAI's current edit reference (and openai-openapi `main`, 2026-11-04) documents a JSON body `images:[{image_url|file_id}]` with `moderation: low|auto`; the multipart schema still lacks it. iota's two edit forms are OpenAI-multipart and xAI-JSON (`image:{url,type}` / `images:[{url}]`); switching `json_edits` on against api.openai.com would answer the probe's 400 (`'images'` missing). So "OpenAI edits plus the xAI JSON variant" is the accurate description of `type: images`, and OpenAI's JSON form is a third, unimplemented spelling — the only one that carries `moderation` on an edit. A follow-up, not this memo's decision.
- **Venice's edit models are invisible to the `images` listing**: `GET /models?type=all` 2026-11-05 → 395 rows, `image` 43, `inpaint` 28 (`firered-image-edit`, `qwen-image-3-pro-edit`, `flux-3-image-edit`, `gpt-image-2-5-sunburst-edit`, `grok-imagine-image-2-0-edit`, …). A Venice type would need its own vocabulary row; the current one is correct for what `images` can call.
- **xAI bills a prompt without an image on `/images/edits`.** A follow-up probe `{"prompt":"x"}` (no `image`, no `model`) answered 200 with a generated URL and `usage.cost_in_usd_ticks: 200000000` (≈ $0.02) — the endpoint falls back to text-to-image. One picture was paid for by this survey, against its own brief; the hazard is recorded here so no test or probe repeats it.
- **OpenRouter's `/images/generations` is an undocumented alias** of `/images` (identical Zod error); the docs name only `/api/v1/images`. Not a reason to rely on it.
