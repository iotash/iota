# 5.2-6 零值语义清理（F8 + F9）

Go 的 `""`/`0`/负数当 `None`、`int` 当计数，在 Rust 里表现为 `i64` 计数与 `Option<String>` 三态。报告建议「逐 struct 推进，不必一次做完」，这里按四片切。

## 6A（已落地）：计数类型（`max_turns`、`context_window`、会话计数）

- `--max-turns`：CLI 行为不变（`i64`，负数 = 无限），但**在 CLI 边界就折成 `Option<NonZeroU32>`**（`None` = 无限；超过 `u32::MAX` 同样视为无限，与现状一致）。`TurnBudget::new(cap: NonZeroU32) -> Arc<TurnBudget>`（`Option` 由调用方 `map`），内部 `remaining: AtomicU32`；`ChatError::LocalCap { turns: NonZeroU32 }`；`run_once` / `tool_loop` / `Delegator` / `OnceRequest` / `DelegateSpec` 的 `max_turns` 全部改 `Option<NonZeroU32>`，循环计数 `rounds: u32`。YAML 里 agent 自己的 `tools.delegate.max_turns` 仍以 `i64` 解析（配置形状不动），解析处折一次。
- `context_window`：内部统一 `u64`，`0` 只在「尚未解析出窗口」这一处出现（`resolve_context_window` 的返回，`ContextBudget::new` 立刻折成 128k 默认）。`Occupancy.window: u64`（与 `settled/pending` 同型，`threshold_of` 变成 `window.saturating_sub(RESERVE).max(window * 80 / 100)`，`status_text` 的 `try_from` 消失），`window()` / `set_window(u64)`、`repl::Startup.context_window`、`TokenStatus.window`、`context_window_rows -> Rows<u64>`、`tokens.rs` 四个常量全部 `u64`。**会话 meta 的 `context_window: i64` 与 record 的 `compacted_through: i64` 是磁盘形状，不动**：loader / writer 各转一次（`u64::try_from(..).ok().filter(|w| *w > 0)`；`usize::try_from(through).unwrap_or(0).min(conv.len())`，与 Go 夹到 0 的结果相同）。
- `append_compaction(.., retain_tail: usize)`：`i64` 只在写 record 的那一行出现。

## 6B（已落地）：`Dispatcher` 能力发现（F9）与 `header_summary` 三态

- `trait Owner { fn owns(&self, name: &str) -> bool }`、`trait ToolSearcher { fn search_tools(&self, query: &str) -> Vec<ToolDef> }`；`Dispatcher::as_owner(&self) -> Option<&dyn Owner>`、`as_tool_searcher(&self) -> Option<&dyn ToolSearcher>`，与 `Provider` 的 `as_*` 同一风格。`Merge` 的「有能力但零命中」不再靠 `Some(vec![])` 表达：`Merge::as_tool_searcher` 在任一 part 有能力时返回 `Some(self)`。
- 删除 `impl Dispatcher for Arc<T>`（45 行逐方法转发，无泛型调用方需要它），统一 `&dyn Dispatcher` / `&*arc`。
- `header_summary -> Option<String>`（`None` = 无能力，`Some("")` = 有能力但只出裸标题）改为 `enum Headline { Untitled, Bare, Detail(String) }`，`Tool` 与 `Dispatcher` 同形。
- `ServerStatus.err: String`（"empty on success"）与 `repl::run` 的同名字段改 `Option<String>`，与同文件 `McpEvent.error` 一致。

## 6C（已落地）：`ProviderConfig` 类型化 accessor

serde struct 继续用 `String`（YAML 兼容、报错时机与 Go 一致），但暴露 `fn effort(&self) -> Result<Option<Effort>, InvalidEffort>` 等 accessor，删掉分散的 `is_empty() + parse`；`Effort::parse` 不再接受 `""`（空由 accessor 处理）；`ImageGenParams` 三个 "Empty means omit" 的 `String` 改 `Option<String>`。

## 6D（已落地）：llm wire 层的 `Option`

范围按「读取点是否在判空」划定，而不是把 91 个 `String` 全换掉：

- **响应侧**（`#[serde(default)]` 的 `String`，读取点在 `is_empty()` 判断）：`RespOutputItem { id, call_id, name }`、`GFunctionCall { id, name }`、`GFunctionResp { id, name }`、Google 模型列表条目的 `name`/`id`。改 `Option<String>`，用一个共享的 `deserialize_with = "none_if_empty"` 把缺席与 `""` 都归一到 `None`（服务端偶尔会发空串），于是 `peeked.call_id.as_deref().unwrap_or(&peeked.id)` 这类读法成立。
- **请求侧**（`skip_serializing_if = "String::is_empty"`，而上游本来就是 `Option`）：`ChatCompRequest.reasoning_effort`、`ChatMsg.tool_call_id`、`GThinkingConfig.thinking_level`、`GImageParams` 三项、`ImagesRequest` / `ImagesEditJsonRequest.size`。改 `Option<String>` + `Option::is_none`，builder 直接传 `Option`，输出字节不变。
- **计数**：`reference_id` / `sample_count` / `partial_images` 改 `Option<u32>`，删掉 `is_zero`。
- **不动**：`description`（四个工具定义 struct）、`GContent.role`、`GPart.text`、`GBlob` / `GImageBlob.mime_type`、`GReferenceImage.reference_type`——这些是请求侧的「必填或整段省略」字段，`""` 就是「没有」，与 JSON `omitempty` 同义；`GPart` 本质是一个 sum type（text | inline_data | function_call | …），真正的修法是 F2/F3 那种 enum，不在本片范围。

## 行为边界

- 无。CLI 文本、会话文件字节、请求 JSON 键序全部不变；每片以 `cargo test` 验证，6A+6B 与 6C+6D 各跑一次全量 CI。

## 落地记录

- **6A**：`chat::turns::turn_cap(i64) -> Option<NonZeroU32>` 是 CLI 与 YAML 两处 `i64` 唯一的折算点；`TurnBudget::new(NonZeroU32) -> Arc<_>`，`remaining: AtomicU32`；`ChatError::LocalCap { turns: NonZeroU32 }`。`context_window` 链路（`resolve_context_window` → `RunParams` → `ContextBudget` → `/status`、`/model` 预设、`/save`）全部 `u64`，`SessionMeta::set_context_window(u64)` 是唯一写回 `i64` 的地方；`replay_session_settings -> Option<u64>`。`SessionWriter.conv_count`、`append_compaction(retain_tail)`、loader 的 `start` 全部 `usize`。**未动**：`SessionMeta.message_count: i64` 与 `SessionInfo.message_count`（只是磁盘值的搬运，没有算术）。
- **6B**：`Owner` / `ToolSearcher` 两个能力 trait + `Dispatcher::as_owner / as_tool_searcher`；`DeferDispatcher` 是唯一的 `Owner`，`SearchingDispatcher` 是唯一的 `ToolSearcher`，`Merged` 在任一 part 有 searcher 时自己也是；`impl Dispatcher for Arc<T>` 删除后只有 `merge.rs` 两处 `flat_map(Dispatcher::x)` 需要改成闭包，其余全靠 auto-deref。`ServerStatus.err` 与 `reqlog::ResponseHalf.err` 改 `Option<String>`。
- **与报告的偏离**：`header_summary` 仍是 `Option<String>`。它实际只有两态——`None` = 工具不写自己的标题、调用方退回参数摘要；`Some(s)` = 工具自己的文本、原样使用（空串就是裸 `[name]`，这是 `edit_file` 不让 `new_string` 进标题的既定行为）。「三态」只是原注释的写法，把注释改成两态的说法即可，不值得为此引入枚举。
- 6A+6B 合跑全量 CI：第一次在 `cargo doc` 步骤失败（新注释里 [`merge`] 在函数与模块之间歧义，改 [`merge()`]），第二次通过：1404 测试，跨二进制往返 `raw_restored=1`。
- **6C**：`Effort::parse` 严格（`""` 也是 `Err`），新增 `Effort::optional` 承接「空 = 未设」的四个边界（`config.yaml`、会话 meta、delegate 工具参数、`/model` 的 default 行）；`ProviderConfig::effort()` / `image_gen_params()` 与 `SessionMeta::effort()` / `image_gen_params()` 是唯一读取原始字符串的地方，六处手写 `is_empty() + parse` 消失。`ImageGenParams` 三项改 `Option<String>`（`from_raw` 归一空串），`/status` 标签、`/model` 的 Aspect/Size/Negative 行、imagen/images 请求 builder 随之改 `if let` / 直接传 `Option`。
- **6D**：`llm::none_if_empty` 取代 `is_zero`；响应侧 `RespOutputItem { id, call_id, name }`、`GFunctionCall` / `GFunctionResp { id, name }`、`ModelsEntry { name, id }` 改 `Option<String>`（`call_id.clone().or_else(|| id.clone())` 取代 `is_empty()` 分支，Gemini 缺 id 时的 `call_{name}_{n}` 生成走 `unwrap_or_else`）；请求侧 `reasoning_effort`、`tool_call_id`、`thinking_level`、`GImageParams` 三项、`ImagesRequest` / `ImagesEditRequest` / `ImagesEditJsonRequest` 的 `size` 改 `Option<String>`，`n` / `partial_images` / `reference_id` / `sample_count` 改 `Option<u32>`；multipart 写入器按 `if let Some` 写字段。请求 JSON 与 multipart 的 golden 测试未改一字节。
