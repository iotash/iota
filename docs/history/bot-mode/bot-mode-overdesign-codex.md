### (b) 删除 `materialized` 整条链

**裁决：做。空 bundle 的代价值得，建议一次删完整条链，不保留旧指针状态的兼容分支。**

最简顺序是：检查配置和 provider → 取 bot 锁 → 读指针；无指针则由现有 `create` 生成 ID → 设置新会话元信息 → 物化 bundle、拿 bundle 锁 → 原子写 `bot.json` → 才交给交互循环。存在指针则 resume，缺本体为 `BotMissing`，读坏仍原样拒绝。`ensure_created` 当前会创建 attachments、日志、锁并写 meta（`writer.rs:348`）；因此所谓“空 bundle”不是只有一份 meta，而是没有对话记录的正常 bundle。

这不是牺牲“本体丢了不能静默重来”：恰恰是让**发布指针之前必须已成功创建本体**成为唯一规则。启动后未说话即退出，只为这个 bot 留一份以后继续用的空会话，不会每次正常重启都多一份。普通 picker 排除 bot 本体；列表/磁盘会多一个可见的空对象，这个产品变化应如实记录，不能声称零成本。

需要保住三个边界：

1. **指针发布失败或之前崩溃**：可能留下无主的空 bundle，下一次启动可另建；此时尚未接受用户轮，所以不会把已说过的话静默遗弃。不为自动回收这点空数据新建垃圾回收器。物化失败不能发布指针，不能把“目录建成”当成整个初始化成功。
2. **两个锁都留**：首次同名 bot 并发仍由 bot 锁串行化；已建 bundle 的独占写仍靠 bundle 锁。别把删除懒创建状态误做成删除独占机制。
3. **测试按行为迁移**：`an_unsaved_pointer_starts_over_under_the_same_id`、`a_resume_fixes_a_stale_materialized_flag`、纯回调测试可随机制删除；但“写盘失败 → backlog 恢复 → 压缩 → 重启不丢轮”的测试必须留。`bot_flush.rs:57`、`:97` 当前用 `OnCreated` 注入故障，应换局部写盘故障注入。仅把一个已打开的日志路径改成目录不保证能阻止旧文件句柄写入，不能机械套用这种替代。

删除范围还包括 `OnCreated`/`on_created`、`never_saved`/`NEVER_SAVED`、stale 标志补正及 `NewSession.id` 的提前指定能力。物化入口只需 session 层内部可用，不必为了五行调用又发布一个通用生命周期 API。

**第三种做法**是“bundle 仍懒建，首次成功物化才发布指针”。它能省 `materialized` 和空 bundle，但必须在第一轮写入前协调指针发布、失败重试、启动阶段 ID/标题/宿主信息；至少保留创建回调或把 bot 初始化状态搬进 loop。推测：实现能比现状短，但无法比启动阶段一次顺序初始化更简单。再换成按 bot 名直接存 bundle 则会触动现有 session 查找、ID 前缀解析和布局，超出这项局部简化的收益。**不选这些替代。**

### (c) 砍长跑 6b、合并 32k 场景、删 ignored 8k

**裁决：有条件做。支持删复杂的 refresh 豁免器、保留一个软阈值长跑、归档 8k 反例；不接受“6a + 当前全程 flush 记账已经保证恢复后的行为相同”这个论证。**

**删掉之后实际失去的覆盖：**

两条旧 bug 的钉子本轮均通过：`a_flush_queued_when_the_process_went_down_runs_after_the_restart`（`bot_flush.rs:1288`），`a_restart_near_the_threshold_still_compacts_before_the_next_message`（`:1226`），以及证明 usage 起作用的 `without_the_measurement_the_restart_would_not_compact`（`:1260`）。它们支撑缩减，不能推出所有未来组合都已覆盖。

**fable 对“定稿 §6 #13”的质疑成立，而且比 reserve/最小窗口更广。** #13 实际列的是 memory/line/summary/note 上限（`bot-mode.md:646`），reserve 和最小窗口另在 §3.6.1/§4.1；不能把两个表项混成一个实验责任。该脚本对这些数值都不具备自动定稿能力：

- 窗口可传，但脚本拒绝小于 32000（`:95`），没有扫描窗口边界，也没有改变 reserve 的实验组。它不能证明精确最小窗口或 reserve 最优；合成长跑也只证明特定负载在 8k 失败、32k 通过，不证明 31999 必败。

- 评分是关键词（`:361`、`:366`），不是对事实、否定、决策理由或过时状态的完整语义评分。一次 20/20 也不等于上限选择得到长期验证。

因此不同意 Opus `:137`、`:181` 的“跑一次便把全部临时值改为定稿”。更诚实也更简单的闭环是：**删未来组 → 跑一次两组试运行检验方向 → 记录已知适用范围；常量由产品基于这些证据选择。** 不要求为“定稿”再建设参数搜索平台；也不让“将来实验会定稿”成为长期悬空的承诺。一次结果不够时继续明确不确定性，合并状态与 L1 事实保留验收状态分开。

### (e) PM 的两处不同意

**保留 frontmatter 的 `bot:` 归属校验：做（必要复杂度）；删除它：不做。** 同意 PM，不同意 Opus `bot-mode-overdesign-opus.md:97`。路径说明“这个文件现在放在哪”，frontmatter 说明“这份可复制的数据自称属于谁”，两个信息并不重复。代码只有一个比较和一条拒绝信息（`memory.rs:504`）；更简单的“以路径为准”会在写入时替另一个 bot 的文件改 owner 并继续使用，失去一次廉价的误拷贝提示。文件没有 `bot:` 仍可作为人写文件采用（`memory/tests.rs:449`），无需新增强制 schema。

但必须校正保证：**当前只拒绝写，不能防止静默读入别人的记忆。** `Snapshot::reload` 经 `BotMemory::read_for_snapshot` 直接读文本并去 frontmatter（`snapshot.rs:64`、`:71`；`memory.rs:684`）；summary 的 `Snapshot::current` 同样直接读（`snapshot.rs:98`）。没有 owner 比较。推测（静态路径推导，本轮未另建复现测试）：拷贝一个 `bot: other` 的文件后，第一次记忆注入可以带上它；直到调用 remember 才会触发现有拒写。

保留现有检查的实际收益是“防止静默改写与改归属”，足够支持保留。若 PM 要兑现“连静默套用也避免”，应让 snapshot 与 summary 读取也复用同一项 owner 检查，沿用已有 warning/不注入路径；不用加新所有权注册表或复杂 schema。这是小的保护闭环，独立记录，不以删校验解决不完整，也不把本评审的合并结论冒充对此风险的全面放行。

**把 L0/L1 合在一个分支视为明确用户要求、不算问题：做。** 设计 `:590` 的“建议两个 PR”不高于本次用户指令。提交顺序本来先有 `6bd31c1` 的 session 基础、`8f3c875` 的摘要修复，再长出 bot 与 memory；分层成长与一次交付可以并存。大 diff 增加评审成本是事实，但不是违反用户已选交付方式的证据。不采纳 fable `:21`、`:173` 的违规归因，也不要求现在拆分支或重写历史；其“早两周”没有本分支 9 月 30 日至 10 月 1 日的提交时间支持。

## 3. 优先级与合并判断

如果只能简化三样，按收益与改动风险排序：

1. **首次启动顺序初始化，删除 materialized 链**，连同 `OnCreated`、never-saved 分支、提前指定 ID 的能力。减少一种磁盘协议状态，正确性规则更容易说明和测试。
2. **删复杂 6b 豁免器，收为一个长跑 + 短的固定回复续跑对照**。接受覆盖收缩，但保住实际发送的代表性行为与不变量 0；不为省测试而削弱产品承诺。
3. **删 retention 的 recall 预留及“该实验定稿所有常量”的承诺**。保留当前可研究的问题，让一次真实结果先于下一轮实验设施打磨。

版本字段、尺寸字段、双写入入口、100 B 限制、过期命名和文档归档是可顺带做的小项。不要把所有小项合成一场必须在合并前完成的大重构。

**当前 HEAD 可从过度设计角度合并。** 上述建议不是新的合并阻断；现存必要复杂度有当前使用者，主要风险在贸然删除时损失持久化与恢复覆盖。(b) 若实施，验首次空启动、发布指针失败、丢本体硬错误和写失败恢复；(c) 若实施，按上述覆盖清单验，不沿用旧 HEAD 的绿色当新版本证据。真实模型保留率与缓存实验仍无本分支已完成的证据，不能宣布对应验收已完成；这不等于为过度设计另加一道收费实验合并门槛。
